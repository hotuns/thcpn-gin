# 数据源代码组织与开发规则

本文是 Agent 开发数据源相关功能时必须遵循的规则，适用于设备创建、配置、同步、遥测、媒体、固件、后台管理及其测试。目标是让不同来源独立演进，让 THCPN 逐步退出时不影响碳汇、LoRaWAN V2 和未来来源。

本文规定代码组织及新增代码约束。当前来源实现已拆为独立 Go 包；公共契约和平台存储编排位于 `internal/datasource/platform`，注册及 HTTP/worker 入口位于 `internal/datasource`。业务身份和交互模型参照 [多来源设备统一交互重构设计](device-integration-refactor-design.md)，仓库通用要求参照 [AGENT.md](../AGENT.md)。发现规则与现有实现冲突时，明确指出差异，按本次任务范围渐进迁移，不擅自扩大重构或改变业务契约。

## 1. 来源、设备类型和连接方式

- `source_family` 表示来源体系；`device_type` 表示设备角色；`product_id` 表示产品。不得相互替代，也不得通过名称、产品字符串、数据流前缀或请求是否成功猜测来源。
- 同一来源可以有多个数据源实例。身份、锁、幂等键、缓存和外部配置版本必须保留数据源命名空间。
- 管理来源通过平台受控映射解析；数据流读取来源通过绑定解析。不得为了统一管理来源而移除合法的多源数据读取能力。
- 当前 THCPN、碳汇直接读写各自 MySQL；LoRaWAN V2 调用设备数据服务 HTTP API。连接方式属于各来源实现细节。
- 平台不接管 MQTT 接入、设备上报解析或实时采集写入。新增来源不得默认扩展这些职责。

## 2. 代码职责和依赖方向

依赖方向如下，公共契约不得反向依赖具体来源：

```text
HTTP / worker / 平台业务调用者
              ↓
平台编排：授权、解析目标、选择能力、记录操作、应用平台结果
              ↓
按能力定义的公共接口与注册表
              ↓
THCPN 实现 / Carbon 实现 / LoRaWAN V2 实现 / 新来源实现
              ↓
各自源库 SQL 或上游 HTTP client
```

### 公共层负责

- 平台设备身份、来源映射、目标授权、平台资源归属和权限。
- 操作生命周期、审计、可重试策略，以及平台快照、数据流和绑定的事务编排。
- 来源能力选择、统一错误分类，以及真实共有的分页、时间范围和结果完整性契约。
- 连接池、超时、密钥解析等无业务语义的基础设施。

### 来源模块负责

- 源端表结构、查询、事务、HTTP 路径、认证细节和错误转换。
- 配置字段、默认配置、版本规则、并发控制和源端幂等处理。
- 外部设备发现、拓扑、指标解释、协议编译和源端结果转换。
- 来源专属功能，例如碳汇周期/地块、LoRaWAN 节点模板和 THCPN 旧配置格式。

来源模块之间禁止直接依赖。碳汇不得调用 THCPN 的业务辅助函数或使用 THCPN 命名的配置 DTO。真正相同且语义稳定的能力，提取到中立公共模块；仅仅字段相似或目前实现相同，不足以构成共享理由。

公共编排通过依赖注入调用来源模块。来源模块可以消费中立的平台存储接口或明确的事务依赖，但不得依赖顶层编排包、HTTP handler 或其他来源包，以免形成循环依赖。

## 3. 目录组织

当前目录职责如下，后续调整必须保持依赖方向，不能产生循环引用：

```text
internal/datasource/
  platform/           中立契约、配置状态、平台存储与通用运行时
  sources/
    thcpn/            THCPN SQL、配置、同步转换及测试
    carbon/           碳汇 SQL、配置、周期查询及测试
    lorawanv2/        HTTP client、节点配置、模板及测试
  ...                 注册、公共编排和平台存储衔接
```

- 独立文件前缀不等于模块隔离。持续演进的来源逻辑应形成独立 Go 包，通过编译依赖限制相互调用。
- 来源专属实现和测试放在对应 `sources/` 包。根包只保留组装、公共编排和 HTTP/worker 入口；不得重新把来源业务实现放回根包。
- 迁移接口时要替换旧调用路径；过渡兼容入口要注明用途和清理条件，不保留两套长期独立工作的业务实现。
- 不在本规则下拆分部署进程、引入插件动态加载或独立微服务。

## 4. 接口与能力

- 按真实变化定义小接口，例如遥测查询、配置读取/写入、发现/同步、固件管理。不得把所有能力塞进一个必须全部实现的 Adapter。
- 不支持的能力明确返回能力不可用，前端据此控制入口。不得调用其他来源作为兜底。
- 注册和能力选择集中管理。允许来源解析、注册及来源专属入口中的显式分派；不得把来源 `switch/if` 散布到通用配置、采集计划、导出和任务流程。
- 新来源不应要求逐一修改所有现有来源实现。确需扩展公共契约时，说明共享语义、兼容方式和对既有来源的影响。
- 通用操作使用中立名称；来源专属类型保留在来源模块。不得继续扩展 `THCPN...` 类型作为其他来源的公共协议。
- 不强制所有来源共享相同配置 JSON。公共接口统一目标、能力、版本令牌和操作结果；具体配置必须有明确的来源、类型及校验规则，不能以任意 `map[string]any` 逃避契约。
- 前端同样按明确的来源选择编辑器、语义校验及保存摘要。Carbon 的原生硬件接口/协议字段不得交给 THCPN 的 sensorType/port 编辑器或校验器；共用 JSON 外层结构与复制选择器不代表共用来源业务规则。为实际源库配置提供脱敏回归样本，验证读取、复制、编辑和保存载荷保留原格式及目标版本。
- 不把 SQL、表名、JSONPath、上游地址、密钥或内部 adapter 配置交给普通前端决定。

## 5. 配置写入与跨系统一致性

每个来源必须分别表达以下事实：

| 阶段 | 表示什么 | 可作为成功依据的证据 |
| --- | --- | --- |
| 源端 | 源库提交或上游服务接受 | 数据库提交结果、上游返回或回读核对 |
| 平台 | 快照、数据流及绑定已应用 | 平台事务提交 |
| 设备 | 硬件实际应用配置 | 协议提供的明确确认或可验证回报 |

- 源端接受不能表达为设备已生效。缺少确认机制时设备状态保持未知；请求时间、保存时间或 `dispatched_at` 不构成硬件确认。
- 涉及外部写入的配置操作必须保留操作 ID、分阶段状态和可追踪错误。各来源实现独立，但操作状态和恢复保障应遵循共同契约。
- 版本控制按来源实现：MySQL 配置可使用源配置 ID 和事务内检查；HTTP 来源使用其实际支持的版本/条件写机制。无上游并发保障时如实说明限制，不伪造跨进程安全。
- 本地锁只能提供其实际进程或部署范围内的保护，不能代替源端并发校验。
- 不假设 MySQL、HTTP 服务和 PostgreSQL 可以原子提交。写入超时或提交结果不明确时标记结果未知，先核对源端，再决定是否重试。
- 源端已成功、平台失败时标记部分成功。恢复应重新读取源端并应用平台，不得自动重复创建外部设备或追加配置版本。
- 配置保存后应应用平台投影，并分别记录源端、平台结果。碳汇配置保存通过公共写入协调器写入源库新版本及对应快照；平台失败通过配置对账恢复，不重复追加源配置。
- 同步、重试和对账必须幂等，保留平台设备 ID、数据流 ID、绑定、归属、分享及导出引用。
- 配置历史是否追加、哪些旧字段必须保留，由来源规则决定，不得因通用转换丢弃未编辑字段。

## 6. 身份、拓扑和平台投影

- THCPN 节点有独立设备身份；LoRaWAN V2 节点由网关和 node index 定位；碳汇 Node、地块属于站内业务对象。共享页面不意味着统一成同一资产结构。
- 外部设备标识使用来源契约，不能把所有来源强制为整数 ID，也不能把网关 SN 与配置版本混用。
- 通用目标必须足以授权：节点编号必须结合所属网关；外部键必须结合数据源；跨设备目标必须校验关系。
- 来源实现把源端结果转换成平台可理解的投影；公共层不直接解释某个来源的原始字段。

## 7. Schema 与迁移

- 平台 SQL 以 `sql/queries/` 为准，修改后运行 `make sqlc`；不得手改生成代码。源库 SQL 放在对应来源模块。
- 平台 schema 修改新增成对 migration，不修改已应用历史迁移，不由普通业务请求临时执行 DDL。
- 新来源接入必须检查所有相关约束和索引：来源分类、映射、快照、配置版本、操作记录、固件与导出等实际涉及项。不能只扩展映射表就认为接入完成。
- 公共表共享的是平台事实，来源专属复杂结构可有专属存储，不为统一而把 THCPN 字段变成全平台强制字段。
- 明确外部键及版本的唯一性作用域。不能假定不同数据源的相同外部 ID 是同一对象。
- 迁移需验证空库升级、存量升级及新增 down/up。回退涉及已有数据时必须说明限制，禁止为通过 down 自动删除已同步数据。

## 8. Agent 实施与验证要求

开始修改前：

1. 阅读本规则、`AGENT.md`、相关现有设计和代码。
2. 确定来源体系、数据源实例、设备/节点目标，以及本次属于公共编排还是来源专属逻辑。
3. 列明受影响的配置、快照、数据流、操作状态和迁移；区分已验证行为和目标设计。

实施时：

1. 优先在对应来源模块内完成改动，避免通过增加公共流程分支解决局部协议问题。
2. 接受可注入依赖，使源端失败、未知结果和平台失败能在测试中复现；避免业务函数内部反复创建全局 Runtime。
3. 接口或 schema 发生变化时同步契约、生成代码及相关文档；不借机修改无关来源和用户未提交文件。

按变更选择验证：

- 来源专属转换/校验测试；公共流程通过相同能力接口验证成功、失败和不支持行为。
- 数据库行为使用 `internal/testdb` 隔离库，确保集成测试实际执行，不能把因缺少环境变量而跳过当成通过。
- 同步测试覆盖首次创建、重复同步及平台身份稳定；配置写入测试覆盖版本冲突、源端成功后平台失败、未知结果核对和恢复不重复写源端。
- HTTP 来源使用可控上游或已授权环境验证契约；不得用生产真实创建设备或下发配置作为默认测试。
- 执行仓库要求的相关测试、生成和构建检查；最终说明实际完成的验证及未验证项。

## 9. 接入和验证入口

- 根包 `modules.go` 注册配置、采集计划、对账、全量同步、运行状态、创建和固件能力；`runtime.go` 注册遥测/媒体查询实现。来源的 SQL/HTTP、版本判断及批量分组留在各来源包。
- `platform.Catalog` 保存注册的来源与连接类型、Adapter 与 payload/mapping 规则。新来源描述由组装入口注入，公共校验不得再增加来源分支。
- 通用传感器模板存储使用中立类型；协议校验、源端配置条目投影分别通过注册的 `TemplateValidator`、`TemplateProjector` 完成。模板写入必须明确提供一个来源 variant，不默认归为 THCPN。来源端模板导入属于各自实现。
- 后台通用配置入口为 `/api/v1/admin/devices/{device_id}/config`，目前由 THCPN、碳汇提供能力；LoRaWAN V2 的网关、节点传感器和时间配置使用自己的模块及 `source-config/{config_kind}` 入口。不得为统一 URL 强行把它们转换成旧库配置格式。
- 不支持的能力返回明确错误；数据源查询错误、停用或未配置不能触发另一来源的兜底。
- 执行 `go test ./...`；配置共享状态及并发改动还需执行相关 race 检查。数据库测试通过 `THCPN_TEST_DATABASE_URL` 指向本地可创建隔离数据库的 PostgreSQL，再执行 `go test ./internal/datasource/... ./internal/firmware ./internal/wallboard`。不得填写生产数据库地址。
- `TestSourcePackageIsolation` 防止来源包互相导入及公共包反向依赖；它不能替代配置、同步和失败恢复的行为测试。

## 10. 评审与退役标准

评审新增来源或重构时检查：

- 是否主要新增该来源模块、注册和必要的迁移，而不修改所有现有来源？
- 是否存在跨来源业务调用、THCPN 类型泄漏、分散分派或公共层解析源端字段？
- 能否通过能力接口测试真实操作及恢复，而无需从外部调用大量来源内部函数？
- 源端、平台和硬件结果是否分别表达？失败后能否安全对账？
- 若移除 THCPN 实现及其注册，碳汇和 LoRaWAN V2 是否仍可编译、运行和测试？

代码可移除不等于数据可删除。退役来源需单独处理历史查询、来源映射、快照、审计、导出和归属保留策略，禁止随代码删除生产历史数据。
